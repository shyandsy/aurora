# design-doc:写技术提议 / 设计 / 架构文档(统一规范)

> **要治的病根**:人容易**按"自己刚想明白"的脑子写**——结论前置、术语不解释、口语吐槽、同一件事说三遍。
> **治法**:按**读者的脑子**写 + **写完强制终检**。这不是靠自觉,是照着这张清单走。

## 第 0 步:先判这是哪种文档(别混)

| 类型 | 什么时候写 | 特征 |
|---|---|---|
| **RFC / 提议** | 方向**未拍板**,要别人评审反馈 | 问题 + 方案 + 备选,1–5 页;**本 skill 默认模板** |
| **ADR**(架构决策记录) | 决定**已拍板**,只记"为什么" | 短(10–20 分钟写完);不可变,改决定就新写一篇 supersede 旧的 |
| **实现方案 / design doc** | 方向已定,写详细怎么做 | 偏 how:接口 / 数据 / 时序 |
| **不用写** | 小改、无依赖 | 直接做,别过度文档化 |

> ⚠️ 已经做完的事别补一篇 RFC "走形式"——那不是求反馈,是橡皮图章,该写 ADR。

## 铁律:为"没有你今天上下文的读者"写

想象读者是**6 个月后才加入、没经历过你这次调试的人**。于是:
- 每个术语 / 缩写 / 内部名(如 PAGE_LABELS、goose、adopt…)**第一次出现必须一句话解释**;
- **不许依赖"你刚 debug 完的记忆"**——背景要自足,别默认读者知道你指的是哪段代码 / 哪个 PR;
- 每个"现状"断言给**出处**(文件 : 行 / 接口 / 迁移名)。

## 固定模板(RFC / 提议)

> 起草时**从本 skill 的 `template/rfc.md` 拷一份改**(ADR 用 `template/adr.md`),别从零排章节——模板已含各节占位、填法提示、和文末的 reviewer 终检清单。

按此**顺序**写,**决策 / 结论收尾,不前置**(别一上来就拿术语砸还没懂问题的读者):

1. **TL;DR** —— 一两句:这是什么、解决什么、提议结论。
2. **背景与问题** —— 症状 + 为什么现在提。先讲清"疼在哪"。
3. **术语速览** —— 本文用到的非通用词,一词一行解释。
4. **原则 / 目标** —— 想达到什么、非目标是什么。
5. **现状** —— 事实,带出处,可用表格。
6. **方案** —— 怎么改。
7. **Alternatives Considered(必含)** —— 认真否过哪些做法、为什么没选。**这是最值钱的一节,别省**;只写 what 不写 why 是最常见的失败。
8. **落地顺序 / 影响 / 回滚** —— 分步;对已部署环境的影响。
9. **开放问题** —— 还没定的点(不是把方案里的模糊处往这甩)。

**ADR 模板**(更短):背景 → 决定 → 理由 → 后果 → 被谁 supersede。

## 语气规范

- 主动语态、陈述句;把短句**连成自然段**,别什么都拆成一堆 bullet。
- **禁**:吐槽 / 情绪化 / 拟人("骗人""踩坑""逼得…渗");含糊词("可能""也许""基本上");反问句;只有你懂的梗。
- **描述事实,不发泄。** effort 配复杂度——简单的事别写成长文。

## 收尾:reviewer 终检(写完必做,逐条过才算完)

起草后,**换"审稿人"视角**单独走一遍这张清单(等价于成熟 RFC skill 的 writer→reviewer 两步;过不了就改,别直接交):

- [ ] 每个术语 / 缩写首次出现都解释了?
- [ ] 同一个观点有没有重复说三遍?(去重)
- [ ] 有没有写 **why** + **Alternatives Considered**?
- [ ] 语气中性,没有吐槽 / 拟人 / 含糊?
- [ ] 结论在**收尾**,没在开头砸读者?
- [ ] 背景**自足**——不靠"你经历过那次调试"也能读懂?
- [ ] 每个现状断言都有**出处**?
- [ ] 长度**配复杂度**,没过度文档化?

## 产出放哪

- **平台级 / 跨项目**(涉及 aurora 本身或多个消费项目):放 aurora `doc/proposals/`。
- **单项目**:放该项目的 `doc/`(design / proposals 下)。
- 写进 git 仓库,不发 claude.ai artifact(除非用户明确要)。
